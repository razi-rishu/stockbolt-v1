0. HEADLINE
--------------------------------------------------------------------------------
  The FINDING is correct: an ordinary authenticated user can UPDATE or DELETE
  their own company's audit_logs today. [VERIFIED]

  The RECOMMENDED FIX is not safe as written. It says "definer posting fns bypass
  RLS" and proposes INSERT WITH CHECK (false). But the accounting posting engine
  writes audit_logs from SECURITY INVOKER functions that run as `authenticated`
  and are subject to RLS. INSERT WITH CHECK (false) would make every one of those
  audit inserts fail; because each is wrapped in a best-effort
  BEGIN…EXCEPTION WHEN OTHERS block, the failure is SWALLOWED and the audit trail
  goes SILENTLY DARK for all confirm/void/reopen/edit/post actions. [VERIFIED]

  => The immutability GOAL is right; the METHOD must differ (keep a tenant-scoped
     INSERT policy; deny only UPDATE/DELETE). See §14. This is the "unexpected
     dependency" the investigation standard says to surface before implementing.


1. IS THE ORIGINAL AUDIT FINDING CORRECT?
--------------------------------------------------------------------------------
  FINDING ("audit_logs editable/deletable by ordinary users"): CORRECT. [VERIFIED]

  Live evidence (all read-only):
   a. Exactly ONE policy on public.audit_logs:
        policyname = tenant_isolation
        cmd        = ALL                 <- covers SELECT/INSERT/UPDATE/DELETE
        roles      = {public}            <- applies to every role
        permissive = PERMISSIVE
        qual       = (company_id = current_user_company_id())
        with_check = (company_id = current_user_company_id())
      (from pg_policies)
   b. NO trigger on audit_logs at all (pg_trigger: 0 non-internal triggers) —
      so there is no immutability enforcement outside the policy.
   c. Table grants (information_schema.role_table_grants):
        authenticated -> SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
        anon          -> same set
   d. RLS state (pg_class): rls_enabled = true, rls_forced = FALSE.
   e. Roles (pg_roles): authenticated.rolbypassrls = false (RLS DOES apply to it);
      anon.rolbypassrls = false; postgres.rolbypassrls = true;
      service_role.rolbypassrls = true.

  [INFERENCE] Combine (a)+(c)+(e): an authenticated user holds the UPDATE and
  DELETE table grants AND the permissive ALL policy passes for rows where
  company_id = their own company. authenticated is not BYPASSRLS, but it does not
  need to be — the policy AFFIRMATIVELY ALLOWS the write. PostgREST exposes row
  UPDATE (HTTP PATCH) and DELETE (HTTP DELETE) on any public table, so:
        DELETE /rest/v1/audit_logs?id=eq.<uuid>     (with a normal user JWT)
        PATCH  /rest/v1/audit_logs?id=eq.<uuid>      body {"new_data": …}
  both succeed within the caller's own company. The one table that must be
  append-only is fully mutable by any logged-in user. (NOT executed — proven
  statically; executing it would tamper with production data.)

  REFINEMENT the audit missed: the recommended fix itself is unsafe (see §0, §4,
  §14). So the finding is right but the proposed remedy is wrong.


2. ROOT CAUSE
--------------------------------------------------------------------------------
  [VERIFIED] audit_logs was given the same generic tenant_isolation policy every
  tenant table gets — a single FOR ALL (cmd=ALL) permissive policy scoped by
  company_id. For an ordinary table that is correct (users read/write their own
  rows). For an AUDIT table it is wrong: "ALL" grants UPDATE and DELETE to the
  very users the log is meant to hold accountable. No SELECT-only / append-only
  differentiation, no immutability trigger, and the broad authenticated
  UPDATE/DELETE/TRUNCATE table grants were never revoked.

  [VERIFIED] The later write-lockdown / read-lockdown RLS migrations (Phases B/C,
  22b) hardened the posting-engine tables but did NOT re-scope audit_logs — its
  live policy is still the single cmd=ALL tenant_isolation policy.


3. CURRENT WORKFLOW
--------------------------------------------------------------------------------
  WRITE (server-side only — no client writes audit_logs): [VERIFIED]
    * The posting/lifecycle RPCs write audit rows in-line, e.g. confirm_invoice:
        ... UPDATE invoices SET status='confirmed' ...;
        BEGIN
          INSERT INTO public.audit_logs (company_id,user_id,action,entity_type,
                     entity_id,new_data) VALUES (v_company_id, v_user_id,
                     'confirm','invoice', p_invoice_id, jsonb_build_object(...));
        EXCEPTION WHEN OTHERS THEN … END;     <- best-effort; never fails the post
      Same shape in void_invoice, confirm_vendor_bill, and the rest.
    * pg_proc census: 60 functions reference audit_logs. The accounting/inventory
      engine ones — confirm_invoice, confirm_vendor_bill, confirm_pos_sale,
      confirm_credit_note, confirm_debit_note, confirm_expense, confirm_grn,
      confirm_inventory_adjustment, confirm_stock_transfer, confirm_bank_transfer,
      confirm_payment, confirm_vendor_payment, all void_*/reopen_*/edit_*/post_*,
      PDC and payroll fns — are SECURITY INVOKER (prosecdef=false). They run as
      the CALLING role (authenticated) → their audit_logs INSERT is subject to
      RLS. [VERIFIED]
    * A SMALL admin subset is SECURITY DEFINER (prosecdef=true), owned by postgres
      (rolbypassrls=true): accept_invite, invite_user, revoke_invite,
      create_role, update_role, delete_role, set_user_role, set_user_active,
      set_user_overrides, merge_brands, reset_company_data. These BYPASS RLS on
      their audit_logs writes. [VERIFIED]
    * reset_company_data (SECURITY DEFINER) legitimately does
        DELETE FROM public.audit_logs WHERE company_id = p_company_id;
      then inserts a 'company_reset' record. Because it runs as postgres
      (bypassrls), it is unaffected by any RLS UPDATE/DELETE denial. [VERIFIED]

  READ (client): [VERIFIED]
    * src/data/supabaseAdapter.ts getAuditLog()      -> .from('audit_logs').select … (Audit Log report, limit 500)
    * src/data/supabaseAdapter.ts getEntityAuditLog() -> .from('audit_logs').select … (per-document Activity feed)
    * No client-side .insert/.update/.delete on audit_logs anywhere in src/.
    * So the client needs SELECT; it never needs client UPDATE/DELETE/INSERT.

  Live volume: audit_logs = 92 rows. [VERIFIED]


4. WHY THE ISSUE EXISTS (and why the audit's fix is wrong)
--------------------------------------------------------------------------------
  [VERIFIED] Cause of the vulnerability: audit_logs inherited the generic
  cmd=ALL tenant policy + broad table grants and was never specialised to
  append-only. Nobody added an immutability control.

  [VERIFIED] Why the audit's recommended fix (FORCE RLS + INSERT WITH CHECK false,
  "definer posting fns bypass RLS") is unsafe:
    (i)  The posting fns are SECURITY INVOKER, not DEFINER. They run as
         authenticated, so RLS applies to THEIR audit inserts. INSERT WITH
         CHECK (false) blocks those inserts. Because each is in a
         BEGIN…EXCEPTION WHEN OTHERS block, the block is silently swallowed and
         the write is lost — audit logging for the whole posting engine goes
         dark with no error. That is a silent regression of the exact control
         H3 is trying to strengthen.
    (ii) FORCE ROW LEVEL SECURITY is a no-op here. FORCE makes RLS apply to the
         table OWNER, but roles with BYPASSRLS still bypass. The owner is postgres
         and postgres.rolbypassrls = true, so FORCE changes nothing for the
         DEFINER path and nothing for the INVOKER path (already governed as
         authenticated). It is harmless but pointless, and it does NOT rescue (i).
  [INFERENCE] The audit author assumed audit_logs is written only by DEFINER
  functions. Live pg_proc shows the opposite for the accounting engine. This is
  precisely why "do not assume the audit is correct" matters here.

  [VERIFIED] The CORRECT method: keep a tenant-scoped INSERT policy (so INVOKER
  functions running as authenticated can still write), keep a tenant-scoped SELECT
  policy (so the Audit Log report + Activity feed still read), and provide NO
  UPDATE and NO DELETE policy (RLS then denies both for non-bypass roles).
  postgres/service_role (bypassrls) — including reset_company_data — continue to
  work. See §14.

10. BUSINESS IMPACT
--------------------------------------------------------------------------------
  [INFERENCE from VERIFIED exposure] Current state: any authenticated user can
  rewrite or erase their own company's audit trail (PATCH/DELETE via PostgREST).
  The audit log is the record of who confirmed/voided/edited financial documents;
  if it is mutable, it cannot be relied on for internal control, dispute
  resolution, or fraud investigation. Fails standard IT general controls
  (immutable audit trail) and undermines the integrity story for a paid,
  multi-tenant accounting product. Likelihood of casual accidental damage is low
  (no UI exposes it), but the INTENTIONAL cover-up path is wide open and trivial
  for anyone who can call the REST API with their own token.
  Post-fix: audit trail becomes append-only for tenant users; tamper path closed.


11. ACCOUNTING IMPACT
--------------------------------------------------------------------------------

14. RECOMMENDED IMPLEMENTATION PLAN  (for approval — NOT implemented)
--------------------------------------------------------------------------------
  GOAL: make audit_logs append-only for tenant users, without breaking reads or
  the invoker-function write path.

  CORE (RLS policy swap on audit_logs ONLY) — additive migration, applied by hand:
    1. DROP the single cmd=ALL policy on audit_logs:
         DROP POLICY IF EXISTS tenant_isolation ON public.audit_logs;
    2. CREATE a SELECT policy (keeps the Audit Log report + Activity feed):
         CREATE POLICY audit_logs_select ON public.audit_logs
           FOR SELECT USING (company_id = current_user_company_id());
    3. CREATE an INSERT policy (keeps SECURITY INVOKER posting-engine logging):
         CREATE POLICY audit_logs_insert ON public.audit_logs
           FOR INSERT WITH CHECK (company_id = current_user_company_id());
    4. Provide NO UPDATE policy and NO DELETE policy -> both are denied for all
       non-bypassrls roles (authenticated, anon). postgres/service_role
       (bypassrls) retain UPDATE/DELETE for admin/maintenance, so
       reset_company_data keeps working.
    (Do NOT add FORCE ROW LEVEL SECURITY — it is a no-op here because the owner is
     bypassrls; adding it would only invite confusion. WHY: FORCE only affects the
     table owner, and postgres already bypasses via rolbypassrls.)

  OPTIONAL DEFENSE-IN-DEPTH (safe, recommended, still additive):
    5. REVOKE UPDATE, DELETE, TRUNCATE ON public.audit_logs
         FROM authenticated, anon;
       Rationale: removes the latent table grants entirely (RLS is the primary
       control for UPDATE/DELETE; this also closes the RLS-immune TRUNCATE grant).
       KEEP SELECT and INSERT grants (needed by readers and invoker functions).
       ASSUMPTION to confirm before doing this: no SECURITY INVOKER function
       needs UPDATE/DELETE on audit_logs. [VERIFIED for the 60 writer fns: they
       only INSERT (and reset_company_data DELETEs, but it is DEFINER/bypassrls,
       independent of the authenticated grant).]

  WHY THIS PLAN (not the audit's):
    * Keeps INSERT (tenant-scoped) → the invoker posting engine keeps logging.
      This is the single most important correction. [VERIFIED necessity.]
    * Keeps SELECT (tenant-scoped) → reports/activity feed unaffected.
    * Omits UPDATE/DELETE policies → tamper denied for tenant users.
    * Preserves reset_company_data via bypassrls → no admin breakage.
    * Additive and reversible → easy rollback.

  NOT chosen — an immutability TRIGGER (BEFORE UPDATE/DELETE RAISE): rejected
    because a trigger fires for ALL roles and would block reset_company_data's
    legitimate DELETE unless it carried a role carve-out — more complex and more
    fragile than the RLS approach. The RLS approach preserves reset automatically.
    [INFERENCE — design trade-off.]

  Delivery: one additive migration file (phase-53), applied BY HAND in the
  Supabase SQL Editor (plain statements; no CONCURRENTLY needed). Patch nothing
  from old migration files — the policy swap is self-contained.

16. ROLLBACK STRATEGY
--------------------------------------------------------------------------------
  Fully reversible, no data touched:
    * To roll back the policy swap: DROP the audit_logs_select / audit_logs_insert
      policies and RECREATE the original tenant_isolation cmd=ALL policy:
        CREATE POLICY tenant_isolation ON public.audit_logs
          FOR ALL USING (company_id = current_user_company_id())
          WITH CHECK (company_id = current_user_company_id());
    * To roll back the optional REVOKE: re-GRANT UPDATE,DELETE,TRUNCATE to
      authenticated, anon.
  No rows are added/changed/removed by this fix, so rollback carries zero
  reconciliation risk in either direction.

## Verdict

  AUDIT CORRECT BUT IMPLEMENTATION SHOULD DIFFER.

  * The finding is VERIFIED live: audit_logs is mutable/deletable by ordinary
    authenticated users (single cmd=ALL policy + authenticated UPDATE/DELETE
    grants + no immutability control + authenticated is not bypassrls). Real,
    high-severity governance/integrity defect.
  * The recommended FIX is unsafe as written: "definer posting fns bypass RLS" is
    false for the accounting engine (those functions are SECURITY INVOKER and run
    as authenticated), so INSERT WITH CHECK (false) would silently disable audit
    logging via the best-effort exception blocks; and FORCE ROW LEVEL SECURITY is
    a no-op because the owner is bypassrls.
  * The CORRECT fix keeps tenant-scoped SELECT + INSERT policies and omits
    UPDATE/DELETE policies (optionally revoking the UPDATE/DELETE/TRUNCATE grants),
    achieving append-only immutability while preserving reads, invoker-function
    logging, and reset_company_data.
