--------------------------------------------------------------------------------
The accounting roadmap (AC-1 through AC-7) is COMPLETE and committed. All
migrations are applied to production. Every phase ships with structural
regression tripwires that run against the live database on every commit.

Two things are NOT done and both need owner action:

  1. TWO DATA REPAIRS ARE STILL PENDING. The migrations that enable them are
     applied, but the repairs themselves have not been run. Two live customers
     currently carry known-wrong inventory figures (details in section 3).

  2. NO BEHAVIOURAL SUITE HAS EVER BEEN EXECUTED. Six suites totalling ~50
     scenarios are written and staging-gated. They have never run, because the
     only configured Supabase target is production and they mutate data. This
     is the single largest quality risk in everything below.

What is proven today: the code exists, is shaped correctly, is permission-gated,
composes the shared posting primitive, and its arithmetic is unit-tested.
What is NOT proven: that these engines actually book correct entries end-to-end
against a real database. That gap is why two live-data defects (section 2) were
found by manual inspection rather than by the test suite.

2. DELIVERED — POST-ROADMAP DATA INTEGRITY (unplanned, found by inspection)
--------------------------------------------------------------------------------
While closing out AC-5C, production showed an inventory variance. Investigating
it uncovered two linked defects in the deferred-COGS (sell-before-buy) path.
Neither was caught by any test. Both are now fixed.

PHASE 63  DEFERRED-COGS FLUSH NEVER FIRED               [DONE]
      Commit   : 02a4fa2
      Migration: 20260731000001_phase63_deferred_cogs_flush_fix.sql [APPLIED]
      Root cause: TWO CONFLICTING DEFINITIONS OF MOVING-AVERAGE COST inside one
                 transaction. confirm_vendor_bill floors negative stock
                 (GREATEST(qty,0)) and computes the correct cost. But
                 tg_recompute_stock_valuation (phase 29, AFTER INSERT FOR EACH
                 STATEMENT) then recomputes the whole partition with an
                 unfloored cc/cq and forces running_avg_cost to 0 whenever a
                 receipt lands cumulative quantity exactly on zero. The flush
                 re-read that 0, hit "IF v_flush_mac <= 0 THEN CONTINUE", and
                 left the row 'pending' forever. Nothing re-scans pending rows,
                 so it never self-healed.
      Effect   : the purchase had already debited Inventory 1300, the sale never
                 recognised COGS, and stock netted to zero — inventory
                 overstated and COGS understated by the full purchase value,
                 silently, on a live customer.
      Fix      : price the flush off the ARRIVING BILL LINE (landed cost
                 included) instead of the post-receipt average. The average is
                 unavailable precisely when it is needed and is not the correct
                 basis anyway — the units that arrived are the ones covering the
                 backorder. Falls back to the running average only when the bill
                 brought no stock for that product. Tracks per-product receipt
                 capacity so partial coverage never credits 1300 for units that
                 have not arrived.
      NOT changed: recompute_stock_valuation and its trigger. Their "no stock,
                 no average" rule is what the E1 health check measures against;
                 changing it would ripple through every valuation surface. The
                 fix removes the flush's DEPENDENCY on it instead.
      Adds     : flush_stranded_deferred_cogs(p_dry_run DEFAULT true,
                 p_post_date DEFAULT null) — composes post_journal_entry,
                 gated on accounting.write, dry-run by default.

PHASE 64  FLUSH NEVER WROTE BACK TO THE SUBLEDGER       [DONE]
      Commit   : 4fbe1b3
      Migration: 20260731000002_phase64_deferred_cogs_subledger_writeback.sql
                                                                   [APPLIED]
      Root cause: phase 63 posted the correct journal entry but nothing wrote
                 the recognised cost back onto the stock_ledger row that
                 recorded the sale. That row was written at MAC 0 and stayed at
                 0 forever.
      Effect   : (a) the subledger never relieves the sale, so it reports more
                 inventory value than the GL; (b) worse, the moving average is
                 then computed off an inflated cumulative cost, so EVERY FUTURE
                 SALE of that part costs too much and the error compounds.
                 IMBD123's BATTERY sat at 224.14 when the true average is
                 216.88 — 7.26 per unit too high, permanently.
      Fix      : write the cost back on flush, then call
                 recompute_stock_valuation explicitly — the valuation trigger
                 is AFTER INSERT ONLY, so an UPDATE does not re-derive the
                 average. The unit_cost = 0 predicate self-sequences the match;
                 one invoice can carry several rows for the same
                 product+warehouse (observed up to 6 in live data), so a naive
                 match would have costed the wrong row.
      Adds     : repair_flushed_cogs_subledger(p_dry_run DEFAULT true) — reuses
                 the flush_unit_cost ALREADY POSTED rather than re-pricing, so
                 it is strictly GL-NEUTRAL: it touches no journal entry and no
                 general_ledger row. Gated on inventory.write (not
                 accounting.write) precisely because it posts nothing.
      HONEST NOTE: phase 64 is a defect in phase 63, shipped hours earlier.
                 Tests D1-D8 did not catch it because they all assert the
                 GENERAL LEDGER, and the ledger was already correct — the
                 defect lived in the subledger. D9 now covers exactly that.

ALSO DIAGNOSED, NO ACTION NEEDED:
      Al Noor's 22.12 inventory variance is NOT an error. Its exact cumulative
      stock cost equals GL 1300 to the cent (1,902,073.56). The variance is
      entirely the E1 health check's own reconstruction: it values stock as
      running_qty x running_avg_cost, and the average is stored to 2 decimals.
      On a 10,300-unit line that rounding is amplified to 36.00. The individual
      drifts (+36.00, -20.00, +5.52, +0.60) sum to exactly 22.12.

P1  FINDINGS FROM THIS WEEK, NOT YET BUILT
    1. Flush coverage gap. The deferred-COGS flush ONLY runs inside
       confirm_vendor_bill. Stock arriving via GRN, stock adjustment, stock
       transfer or opening balance never flushes a deferred row at all — same
       bug class as phase 63, different door. repair_flushed_cogs_subledger and
       flush_stranded_deferred_cogs are the manual remedies today.
    2. recompute_stock_valuation(p_company_id) is SECURITY DEFINER and
       executable by `authenticated`, and trusts a caller-supplied company id.
       Not a data leak (it only rewrites derived columns from that tenant's own
       rows) but it is a cross-tenant write primitive. Should derive the tenant
       from current_user_company_id().
    3. Negative MAC renders phantom inventory value. Al Noor's SHOCK shows
       -180 units at -1866.67, which multiplies to +336,000 on valuation
       reports — positive value for stock that does not exist.
    4. E1 tolerance is a flat threshold; it should scale with quantity, or
       large-volume tenants will always drift (see Al Noor above).

  - Any multi-tenant interaction under load.

6. CONVENTIONS HELD THROUGHOUT
--------------------------------------------------------------------------------
  - Migrations are additive and idempotent; code never runs DDL; the owner
    applies every migration by hand.
  - Posting RPCs are patched from the LIVE pg_get_functiondef, never from the
    migration files, so an out-of-date file cannot silently revert production.
  - New posting engines COMPOSE post_journal_entry (balance, period lock, JE
    numbering, audit) rather than duplicating ledger logic. Tripwires enforce
    this by asserting the RPC contains no direct general_ledger INSERT.
  - Repairs default to DRY RUN.
  - Behavioural suites are staging-gated and never wired into the pre-commit
    hook.
  - Commits only on explicit approval; the owner runs git push.
