HIGH
----

F5. Many actions don't check the user's permission. 83 change-making
    functions never call has_perm.
  - The engine functions are covered by RLS: post_journal_entry,
    confirm_invoice, void_invoice and reverse_journal_entry run as the calling
    user, so table permissions still apply.
  - But the ledger tables let any writing role in. phase24
    (20260619000017...) lets anyone with ANY write permission insert into the
    ledger tables (has_any_write()). So a Counter or Sales user can probably
    post or reverse manual journal entries by calling the function directly.
    This is the deferred "posting-gates" item. Static evidence only; confirm
    on staging.
  - Three functions bypass RLS and check no permission at all:
      * delete_role (phase23_custom_roles.sql): any user, even a Viewer, can
        delete a custom role in their own company.
      * record_einvoice_document and cancel_einvoice_document
        (phase59_ac4c...): any role can record or cancel an e-invoice.
      * All three stay inside the caller's own company.
  - Checked and fine: all 74 functions that bypass RLS set search_path. The
    two that take a company ID as input, api_current_stock and
    company_has_api_access, are locked to service_role.

F6. Tests read production with the master key, and CI runs no tests at all.
  - Pre-commit hook: .husky/pre-commit runs test:regressions (402 tests)
    against production using SUPABASE_SECRET_KEY. That reads across every
    company, including verify_invariants for each one.
  - CI: .github/workflows/ci.yml only typechecks and builds.

F7. The staging runbook has risks of its own (docs/STAGING_SETUP.txt):
  - It overwrites .env.local in place, so forgetting to switch back is easy.
  - It says 150 migrations; there are 191.
  - `npx supabase link` decides where `db push` goes. Many prod changes were
    applied by hand in the SQL editor, so prod's migration history probably
    doesn't match the files. A `db push` while linked to prod could try to
    replay migrations on live data.
  - The runbook already warns prod functions were patched from their live
    code, so a database rebuilt from the files may differ from prod.

F8. Onboarding isn't all-or-nothing (src/core/onboarding.ts). Setup runs as
    separate calls from the browser, so a failure partway leaves a
    half-set-up company.

PART D - CHECKING THE TAX IMPACT WITHOUT READING CUSTOMER DATA
================================================================================
Rashid can run one query in the SQL editor. It returns only counts - no names,
amounts or IDs:

SELECT c.country_code,
       count(DISTINCT c.id)                                   AS companies,
       count(DISTINCT tr.id) FILTER (WHERE tr.rate = 5)       AS rates_at_5pct,
       count(DISTINCT c.id) FILTER (WHERE EXISTS (SELECT 1 FROM tax_rates t2
             WHERE t2.company_id = c.id GROUP BY t2.rate HAVING count(*) > 1)) AS companies_with_dup_rates,
       count(ii.id) FILTER (WHERE ii.tax_rate = 5)            AS invoice_lines_at_5pct
FROM companies c
LEFT JOIN tax_rates tr     ON tr.company_id = c.id
LEFT JOIN invoices i       ON i.company_id = c.id AND i.status = 'confirmed'
LEFT JOIN invoice_items ii ON ii.invoice_id = i.id
WHERE c.country_code IN ('SA','BH','KW','QA')
GROUP BY c.country_code;

- All four counts zero: fixing the seed going forward is enough.
- Otherwise: any correction to posted documents must go through credit notes
  or reversals that follow Doc 3. Rashid decides, per company.
