2. ROOT CAUSE
--------------------------------------------------------------------------------
  [VERIFIED] Observability and DR were never set up: no error-tracking SDK was
  added to the app or the Edge Function, the ErrorBoundary's "send to Sentry" step
  was left as a TODO, the Edge catch was written to fail soft (discard the error,
  return a response) rather than report it, and no backup/restore runbook was
  authored. [INFERENCE] For a solo-built product on managed platforms (Vercel +
  Supabase), the platforms' own dashboards (Vercel logs, Supabase function logs,
  automatic daily backups) create a false sense of coverage — they exist but are
  ephemeral, un-alerted, and (for restore) unproven, so nothing surfaces a
  production exception or guarantees recoverability.


3. CURRENT WORKFLOW
--------------------------------------------------------------------------------
  [VERIFIED]
   Client error: a React render error -> ErrorBoundary shows a fallback UI and
     console.errors (no upload). A non-React error / unhandled rejection -> no
     handler at all. The operator may see a broken screen; the team learns
     nothing unless the operator reports it.
   Server (Edge API) error: caught at the top level, the exception discarded, a
     response returned; the request row goes to api_request_log. Supabase also
     captures function console output in its platform logs (ephemeral, no alert).
   DB failure / data loss: reliance on Supabase's managed backups; no documented
     restore procedure, no tested drill, no stated RPO/RTO.
   Uptime: nothing checks that the app or the API is up; an outage is discovered
     by a customer.
   Existing partial signals (NOT error tracking or alerting): api_request_log
     (API request metering), audit_logs (in-app activity trail), webhook_logs
     (PayPal webhook events). [VERIFIED these tables exist.]


4. WHY THE ISSUE EXISTS
--------------------------------------------------------------------------------
  [VERIFIED] The building focus was features and correctness (the accounting
  engine, RLS, the regression suite), not operations. Error tracking, alerting,
  uptime checks, and a restore drill are cross-cutting operational concerns that
  were deferred; the ErrorBoundary TODO and the fail-soft Edge catch are the
  visible residue of that deferral. [INFERENCE] No enterprise/auditor review has
  yet forced the DR runbook + RPO/RTO that such sign-off requires.

10. BUSINESS IMPACT
--------------------------------------------------------------------------------
  [VERIFIED gap / INFERENCE severity] Production exceptions are known only when a
  customer reports them (client errors console-only; server errors swallowed;
  no alerts). An outage is discovered by customers, not by the team. Most
  seriously for a system of record: "we can restore the books" is UNPROVEN — no
  documented procedure, no tested drill, no stated RPO/RTO — so a data-loss event
  (accidental delete, corruption, region incident) has an unknown and unrehearsed
  recovery path. This blocks enterprise/auditor sign-off and is a trust/continuity
  risk, even though it does not by itself corrupt any current data. [INFERENCE.]


11. ACCOUNTING IMPACT
--------------------------------------------------------------------------------
  [VERIFIED] H6 changes no posting/GL code; zero direct accounting impact.
  [INFERENCE] Indirectly large: without error tracking, an exception that
  produces a wrong or missing posting can run unnoticed (the same silent-
  wrongness class as H2/E1); without a proven restore, a corruption event to the
  ledgers may be unrecoverable to a known-good point. Monitoring + DR are
  protective controls for accounting integrity, not changes to it.


12. INVENTORY IMPACT
--------------------------------------------------------------------------------
  [VERIFIED] None direct. [INFERENCE] Same shape as §11 — a swallowed error in a
  stock-affecting path (confirm/adjust/transfer) could corrupt MAC/on-hand
  unnoticed, and an unproven restore leaves no rehearsed recovery. Protective, not
  corrective.


13. RISK ASSESSMENT
--------------------------------------------------------------------------------
  Status quo: MEDIUM-HIGH (operational). Blind to production errors (client
    console-only, server swallowed), blind to outages (no uptime check), and
    unproven on recovery (no tested/documented DR). Likelihood of an
    unnoticed-error or unrehearsed-recovery event rises with customer count.
    [VERIFIED gaps; INFERENCE severity.]
  The DR leg is the highest-severity part: for a book of record, an
    untested restore is an existential continuity risk. [INFERENCE.]
  Risk of the fix: LOW and mostly additive/external. Adding Sentry, an uptime
    monitor, and a DR runbook changes no business logic; the restore DRILL should
    be run against a NON-production copy to avoid touching live data; enabling
    PITR is a cost, not a risk.


14. RECOMMENDED IMPLEMENTATION PLAN  (for approval — NOT implemented)
--------------------------------------------------------------------------------
  The audit's fix is sound; sequence it and fold in the two refinements:

  A. Error tracking (app + Edge):
     1. Add an error-tracking SDK (e.g. Sentry) to the browser app: init in
        main.tsx; wire ErrorBoundary.componentDidCatch to report (replacing the
        console-only TODO); add a global unhandledrejection/error handler.
     2. Add error reporting to the Edge Function and STOP swallowing: capture the
        currently-discarded `_e` (report + log) before returning the 500.
     WHY: makes production exceptions visible to the team, on both surfaces.
     DEP: a DSN secret; CSP (M1) must allow the ingest origin.

  B. Uptime monitoring:
     3. Add an external uptime monitor on the app URL and an API health target.
        Because /v1/me is API-key-gated, either provision a dedicated monitoring
        key or add a small UNAUTHENTICATED health route. WHY: detect outages
        before customers do.

  C. Backup / DR (the highest-value leg):
     4. Confirm/ENABLE Supabase backups + PITR (a plan/cost decision — verify the
        current plan first).
     5. Perform a RESTORE DRILL against a NON-production project and DOCUMENT it
        in docs/DISASTER_RECOVERY.md with stated RPO/RTO and step-by-step restore.
     WHY: turns "we can restore" from a hope into a tested, written procedure —
     the thing enterprise/auditor sign-off requires.

  For each item the WHY is stated; the load-bearing ASSUMPTIONS are (i) the
  Supabase plan supports PITR (or a cost is accepted), (ii) a non-prod project
  exists for the drill (or one is created), (iii) a Sentry-class service is
  acceptable. None are verified here — confirm before implementing.

## Verdict

  AUDIT CORRECT.

  * Verified: no error-tracking dependency, no external error reporting, no global
    client error handler, no alerting, no uptime monitoring, and no documented or
    tested backup/DR (no DISASTER_RECOVERY.md, no RPO/RTO, no restore drill).
  * Refinements (which reinforce, not contradict, the finding): a React
    ErrorBoundary exists but only console.errors (team gets no telemetry), and the
    Edge Function's top-level catch actively SWALLOWS the exception (`_e` unused) —
    so server errors are discarded, not merely unmonitored.
  * The recommended fix (Sentry on app + Edge; confirm/enable PITR; documented
    restore drill with RPO/RTO; uptime monitoring on the app and /v1/me) is
    appropriate. Implementation should fold in two specifics the high-level fix
    implies: stop swallowing the Edge `_e`, and note /v1/me is auth-gated (needs a
    monitoring key or a public health route) — enhancements to the same plan, not
    a different one.
